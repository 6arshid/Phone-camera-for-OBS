# OCP/1 — مشخصات پروتکل دوربین گوشی برای OBS

نسخه: `ocp/1` (عدد نسخه‌ی پروتکل `1`)
وضعیت: پیاده‌سازی‌شده در همین مخزن (افزونه‌ی دسکتاپ = سرور، اپلیکیشن موبایل = کلاینت).

این سند **قرارداد** میان افزونه‌ی دسکتاپ، اپلیکیشن اندروید، اپلیکیشن iOS و
تست‌های خودکار است. هر پیاده‌سازی موظف است دقیقاً از آن پیروی کند.

> این سند ترجمه‌ی فارسی `PROTOCOL.md` است. در صورت تعارض، **نسخه‌ی انگلیسی
> مرجع نهایی** محسوب می‌شود.

---

## ۱. نقش‌ها، لایه‌های انتقال و پورت‌ها

| نقش | موجودیت | روی چه چیزی گوش می‌دهد | به چه چیزی وصل می‌شود |
|------|--------|----------------------|---------------------|
| **سرور** | افزونه‌ی OBS (`obs-phone-camera`) | TCP `47100` (کنترل)، UDP `47101` (رسانه)، UDP `47109` (کشف) | — |
| **کلاینت** | اپلیکیشن گوشی | UDP `47109` (کشف) | TCP سرور `47100`، و ارسال رسانه به UDP سرور `47101` |

* همه‌ی پورت‌ها در JSON به صورت **اعشاری و ترتیب میزبان** هستند؛ سربرگ‌های
  دودویی از **ترتیب شبکه (بزرگ‌ترتیب)** استفاده می‌کنند.
* پورت‌های پیش‌فرض در منبع OBS (بخش «پیشرفته») قابل تغییرند. سرور پورت UDP
  رسانه را داخل `auth_ok` به کلاینت اعلام می‌کند، بنابراین ممکن است با
  `tcp+1` متفاوت باشد.
* همه‌چیز مخصوص شبکه‌ی محلی است؛ هیچ مؤلفه‌ی ابری وجود ندارد.
* خانواده‌ی آدرس‌ها: IPv4 (اصلی). در `ocp/1` از IPv6 استفاده نمی‌شود.

## ۲. کشف (UDP پورت ۴۷۱۰۹)

بسته‌های کشف، **دیتگرام‌های JSON رمزگذاری‌نشده** هستند (رمز و رازی در آن‌ها
نیست). هر دو طرف `0.0.0.0:47109` را با `SO_REUSEADDR`/`SO_BROADCAST` باز
می‌کنند و علاوه بر آن به `255.255.255.255:47109` و به گروه چندپخشی
`239.255.74.79:47109` نیز ارسال می‌کنند.

اعلام سرور (هر ۲ ثانیه تا وقتی دست‌کم یک منبع وجود دارد):

```json
{"t":"obs","v":1,"id":"<32-hex instance id>","name":"DESKTOP-NAME","tcp":47100,"udp":47101}
```

اعلام کلاینت (هنگامی که اپ در حالت بیکار/در انتظار است، هر ۲ ثانیه):

```json
{"t":"phone","v":1,"id":"<32-hex device id>","name":"Pixel 7","os":"android","proto":"ocp/1"}
```

توضیح فیلدها:

* `t` — نوع پیام: `"obs"` | `"phone"`.
* `v` — نسخه‌ی پروتکل، در حال حاضر `1`.
* `id` — شناسه‌ی تصادفی پایدار ۱۲۸ بیتی، هگس کوچک (۳۲ نویسه).
* `name` — نام قابل‌نمایش دستگاه/میزبان (UTF-8، حداکثر ۶۴ بایت).
* `tcp` — پورت کنترل سرور (فقط در اعلام سرور).
* `udp` — پورت **رسانه** سرور (فقط در اعلام سرور). این پورتی است که گوشی
  بسته‌های رسانه را به آن می‌فرستد (پورت پایه‌ی رسانه، به‌طور پیش‌فرض
  `47101`)؛ این پورتِ کشف (`47109`) **نیست**.
* `os` — `"android"` | `"ios"` (فقط در اعلام گوشی).

گیرنده باید دیتگرام‌هایی را که تجزیه‌ی JSON در آن‌ها شکست می‌خورد، دارای `t`
ناشناخته هستند یا `v != 1` دارند، نادیده بگیرد.

## ۳. کانال کنترل (TCP)

چیدمان بایتی قاب (همه‌ی اعداد صحیح بزرگ‌ترتیب):

```
offset  size  field
0       4     magic  = ASCII "OCP1"
4       4     u32    payload length N (1 .. 65536)
8       1     u8     flags   bit0 = payload encrypted
9       2     u8[2]  reserved = 0
11      16    u8[16] tag (HMAC-SHA256/128 truncated), zeros when flags.bit0 = 0
27      N     payload (JSON, UTF-8)
```

اندازه‌ی کل سربرگ = **۲۷ بایت**.

### ۳.۱ رمزگذاری قاب‌های کنترل

پیش از آن‌که سرور `auth_ok` را بفرستد، قاب‌ها متنی‌اند (`flags = 0`، `tag = 0`).

از `auth_ok` به بعد، **هر دو جهت** همه‌ی payloadها را رمزگذاری می‌کنند:

* ماده‌ی کلید در بخش §4 استخراج می‌شود.
* `k_ctrl_enc` = ۳۲ بایت اول `HKDF(master, salt, "ocp1-ctrl", 64)`
* `k_ctrl_mac` = ۳۲ بایت آخر همان ۶۴ بایت.
* رمز: ChaCha20 (RFC 8439)، nonce = `u64 frame_counter` (کوچک‌ترتیب، ۸ بایت)
  ++ `0x00`*4 — یعنی nonce دوازده‌بایتی، شمارنده‌ی کوچک‌ترتیب در ۸ بایت
  پایینی است.
  * شمارنده‌های قاب **در هر جهت مستقل‌اند** و برای نخستین قاب رمزشده‌ی همان
    طرف از صفر شروع می‌شوند.
* `tag` = ۱۶ بایت اول
  `HMAC-SHA256(k_ctrl_mac, frame_header[0..26] با صفر شدن فیلد tag || ciphertext)`.
* گیرنده موظف است قابی را که tag آن نامعتبر است یا شمارنده‌اش به طور سخت‌گیرانه
  از آخرین شمارنده‌ی پذیرفته‌شده بزرگ‌تر نیست، رد کند.

### ۳.۲ ماشین حالت دست‌دهی (کلاینت = گوشی، سرور = افزونه‌ی OBS)

```
client -> server : hello          (plaintext)
server -> client : challenge      (plaintext)
client -> server : auth           (plaintext)
server -> client : auth_ok        (plaintext)   <- keys confirmed, media port sent
client -> server : ready          (encrypted)
server -> client : config         (encrypted, may repeat)
client -> server : stats          (encrypted, 1 Hz while streaming)
server -> client : hint           (encrypted, 1 Hz while streaming)
server -> client : ping           (encrypted)
client -> client : pong           (encrypted)
either  -> either: error          (plaintext or encrypted, then close)
either  -> either: bye            (encrypted, then close)
```

**hello** (کلاینت ← سرور)

```json
{"type":"hello","proto":"ocp/1","kdf":"hkdf-sha256","iter":0,
 "salt":"<32-hex>","nonce":"<32-hex>",
 "device":{"id":"<32-hex>","name":"Pixel 7","os":"android","app":"1.0.0"}}
```

* `kdf = "hkdf-sha256"` → از رمز ازپیش‌تنظیم‌شده به‌طور مستقیم استفاده می‌شود
  (رمز QR یا رمز ذخیره‌شده‌ی دستگاه از جفت‌سازی قبلی). مقدار `iter` باید `0`
  باشد.
* `kdf = "pbkdf2-sha256"` → رمز، همان کد شش‌رقمی جفت‌سازی است که با
  `PBKDF2-HMAC-SHA256(password = ارقام ASCII کد، salt = بایت‌های salt از قاب
  hello، c = iter، dkLen = 32)` کشیده می‌شود. مقدار `iter` باید ≥ ۱۰۰۰۰۰
  باشد؛ سرور از مقدارِ داخل قاب استفاده می‌کند (و `iter < 100000` را رد
  می‌کند).
* `salt` — ۱۶ بایت تصادفی، هگس‌شده.
* `nonce` — ۱۶ بایت تصادفی، هگس‌شده (nonce کلاینت).

**challenge** (سرور ← کلاینت)

```json
{"type":"challenge","nonce":"<32-hex>","kdf":"<echo>","iter":<echo>}
```

* `nonce` — ۱۶ بایت تصادفی (nonce سرور).

هر دو طرف اکنون محاسبه می‌کنند:

```
master        = PSK (see below)
transcript    = SHA256( hello_payload_bytes || challenge_payload_bytes )
salt_kdf      = client_nonce (16B) || server_nonce (16B)
k_auth        = HKDF-SHA256(master, salt_kdf, "ocp1-auth",   32)
k_ctrl        = HKDF-SHA256(master, salt_kdf, "ocp1-ctrl",    64)
k_media       = HKDF-SHA256(master, salt_kdf, "ocp1-media",   64)
```

تعیین `master` در **سرور**:

1. `hello.device.id` در جدول دستگاه‌های جفت‌شده‌ی ذخیره‌شده جست‌وجو می‌شود؛
   اگر پیدا شد، `master = رمز ذخیره‌شده`.
2. وگرنه اگر `kdf == "hkdf-sha256"` و در این لحظه رمز QR معتبر باشد،
   `master = qr_secret`.
3. وگرنه اگر `kdf == "pbkdf2-sha256"` و کد جفت‌سازی در این لحظه معتبر باشد،
   `master = PBKDF2(code, salt, iter, 32)`.
4. وگرنه ← ارسال `error {code:"pairing_failed"}` و بستن اتصال.

در **کلاینت**، `master` یکی از این‌هاست: رمز QR، یا `PBKDF2(کد، …)`، یا رمزی
که کلاینت پس از یک جفت‌سازی موفق قبلی ذخیره کرده است.

**auth** (کلاینت ← سرور)

```json
{"type":"auth","nonce":"<32-hex>","proof":"<64-hex>"}
```

* `nonce` — همان nonce پیام hello کلاینت را تکرار می‌کند.
* `proof` = `HMAC-SHA256(k_auth, "phone" || client_nonce || server_nonce ||
  transcript)` (۶۴ نویسه‌ی هگس).

**auth_ok** (سرور ← کلاینت)

```json
{"type":"auth_ok","session":"<32-hex>","media_port":47101,
 "proof":"<64-hex>","paired":true}
```

* `session` — ۱۶ بایت تصادفی، شناسه‌ی این نشست (در همه‌ی بسته‌های رسانه
  استفاده می‌شود).
* `media_port` — پورت UDP برای بسته‌های رسانه.
* `proof` = `HMAC-SHA256(k_auth, "obs" || server_nonce || client_nonce ||
  transcript)`.
* `paired` — وقتی سرور این دستگاه را (تازه) به‌عنوان جفت‌شده ذخیره کرده باشد،
  `true` است.

در صورت شکست تأیید proof، کلاینت موظف است `error {code:"auth_failed"}` بفرستد و
اتصال را ببندد.

**ready** (کلاینت ← سرور) — گزارش قابلیت‌ها، که پس از `auth_ok` یک بار فرستاده
می‌شود:

```json
{"type":"ready","caps":{
  "video":{"codec":["h264"],"resolutions":[[3840,2160],[1920,1080],[1280,720],[640,360]],
           "fps":[60,30,24],"aspect_ratios":["4:3","16:9"],"max_bitrate_kbps":50000},
  "audio":{"codecs":["pcm_s16le"],"sample_rates":[48000],"channels":[1]},
  "cameras":[{"id":"back","label":"Back"},{"id":"front","label":"Front"}],
  "features":{"torch":true,"manual_focus":true,"exposure":true,"white_balance":true}}}
```

**config** (سرور ← کلاینت) — وضعیت کامل؛ یک بار پس از `ready` و سپس هر بار که
کاربر ویژگی‌ای را تغییر می‌دهد فرستاده می‌شود. کلاینت موظف است کلیدهای ناشناخته
را نادیده بگیرد.

```json
{"type":"config",
 "video":{"codec":"h264","width":1920,"height":1080,"fps":30,
          "bitrate_kbps":4000,"gop_s":2,"camera":"back",
          "orientation":"auto"},
 "camera":{"focus_mode":"auto","focus_distance":0.5,
           "exposure_mode":"auto","exposure_bias":0.0,
           "wb_mode":"auto","wb_kelvin":5500,"torch":false},
 "audio":{"enabled":false,"sample_rate":48000,"channels":1},
 "stream":{"active":true}}
```

توضیح فیلدها:

* `video.camera` — `"back"` | `"front"` | `"toggle"` (toggle یعنی تعویض به
  دوربین دیگر **بدون** اتصال مجدد یا مقداردهی دوباره‌ی نشست).
* `video.orientation` — `"auto"` (سنسور)، `"portrait"`، `"landscape"`.
  این کلاینت است که باید پیش از رمزگذاری، فریم‌ها را بچرخاند تا بیت‌استریم از
  قبل جهت‌دهیِ خواسته‌شده را داشته باشد.
* `video.width/height` — اندازه‌ی خروجی درخواستی. کلاینت نزدیک‌ترین اندازه‌ی
  پشتیبانی‌شده ≥ مساحت درخواستی را برمی‌گزیند و اندازه‌ی واقعی را از طریق
  نخستین فریم رمزگشایی‌شده / `stats` گزارش می‌کند.
* `video.bitrate_kbps` — هدف رمزگذار؛ مقدار `0` یعنی «کلاینت یک مقدار پیش‌فرض
  انتخاب کند».
* `video.gop_s` — فاصله‌ی کلیدی‌بودن فریم‌ها به ثانیه (کلاینت آن را به فریم
  رند می‌کند).
* `camera.focus_mode` — `"auto"` | `"continuous"` | `"manual"`.
  `focus_distance` در بازه‌ی [0,1] (۰ = نزدیک، ۱ = دور) و در حالت دستی
  استفاده می‌شود.
* `exposure_mode` — `"auto"` | `"manual"`؛ `exposure_bias` بر حسب EV (۲− تا
  ۲+).
* `wb_mode` — `"auto"` | `"manual"`؛ `wb_kelvin` از ۲۵۰۰ تا ۱۰۰۰۰.
* `audio.enabled` — پخش میکروفون. وقتی `false` باشد، کلاینت موظف است ارسال
  بسته‌های صدا را متوقف کند.
* `stream.active` — `true` یعنی تولید رسانه را شروع کن؛ `false` یعنی تولید
  رسانه را متوقف کن اما نشست را نگه دار.

**stats** (کلاینت ← سرور، هر ۱ ثانیه هنگام `stream.active`)

```json
{"type":"stats","fps":29.8,"bitrate_kbps":3980,"frames":1234,
 "battery":72,"thermal":"nominal","camera":"back",
 "ts_rel_ns":5000000000}
```

* `ts_rel_ns` — نانوثانیه از لحظه‌ای که کلاینت جریان را آغاز کرده است (مهر
  زمانی رسانه از همان ساعت استفاده می‌کند، به §5 مراجعه کنید).

**ping / pong**

```json
{"type":"ping","t":<unix ms>}      {"type":"pong","t":<unix ms>}
```

**hint** (سرور ← کلاینت، حدود ۱ ثانیه هنگام پخش؛ کلاینت ممکن است آن را نادیده
بگیرد)

```json
{"type":"hint","loss_pct":2.5,"rtt_ms":12,"queue_ms":30}
```

* `loss_pct` — درصد فریم‌های رسانه‌ای که سرور در بازه‌ی اخیر نتوانسته بازسازی
  کند؛ `rtt_ms` — زمان رفت‌وبرگشت کنترل؛ `queue_ms` — عمق صف رمزگشایی سمت
  سرور بر حسب میلی‌ثانیه.
* کلاینت ممکن است از این برای نرخ‌بیت تطبیقی استفاده کند: کاهش `bitrate_kbps`
  به میزان ۲۰٪ وقتی `loss_pct > 5`، و افزایش به میزان ۱۰٪ (هرگز بیش از هدف
  پیکربندی‌شده) پس از ۱۰ ثانیه‌ی پیاپی با `loss_pct < 1`. تطبیق نباید
  وضوح یا نرخ فریم را تغییر دهد و نباید رمزگذار را بیش از هر ۲ ثانیه یک بار
  بازپیکربندی کند.

**error**

```json
{"type":"error","code":"pairing_failed","msg":"Pairing code rejected"}
```

کدهای استاندارد: `pairing_failed`، `auth_failed`، `protocol_error`،
`unsupported`، `busy`، `internal`.

**bye** — `{"type":"bye","reason":"shutdown"}`؛ هر دو طرف می‌توانند پیش از
بستن اتصال TCP آن را بفرستند.

## ۴. کانال رسانه (UDP)

هر دیتگرام = یک بسته. سربرگ (۳۲ بایت، **بزرگ‌ترتیب**، متنی اما به‌عنوان
داده‌ی اضافی تأیید هویت‌شده):

```
offset  size  field
0       4     magic = ASCII "OCPM"
4       1     u8    version = 1
5       1     u8    stream  (0 = video, 1 = audio)
6       1     u8    flags   (bit0 = keyframe)
7       1     u8    reserved = 0
8       8     u64   session tag = first 8 bytes of session id
16      4     u32   frame id (per stream, starts at 1, increments by 1 per media frame)
20      2     u16   fragment index (0-based)
22      2     u16   fragment count (>=1)
24      8     u64   timestamp, nanoseconds relative to stream start (client clock)
32      var   ciphertext (datagram_len - 32 - 16 bytes)
end-16  16    HMAC-SHA256/128 tag
```

* دیتگرام نباید در مجموع از **۱۲۰۰ بایت** بیشتر شود (امن زیر MTU برابر ۱۵۰۰
  در Wi-Fi). ⇒ ciphertext حداکثر ۱۱۵۲ بایت؛ payload یک فریم به
  `ceil(len / 1152)` قطعه تقسیم می‌شود.
* شماره‌ی فریم‌ها **در هر جریان مستقل‌اند**: فریم‌های ویدیو `1,2,3,…` و
  فریم‌های صدا `1,2,3,…` را به‌طور مستقل می‌شمارند (هر دو دنباله در همان فیلد
  `frame_id` ظاهر می‌شوند؛ فیلد `stream` آن‌ها را از هم تفکیک می‌کند).
* nonce مربوط به ChaCha20 (۱۲ بایت، بزرگ‌ترتیب) =
  `session_tag[0..4) || u8 stream || u32 frame_id || u16 frag_idx || 0x00`.
  بنابراین هر بسته nonce تازه‌ای دارد (کلید یکتا در هر نشست + سه‌تایی یکتای
  `(stream, frame_id, frag_idx)`).
* `tag` = ۱۶ بایت اول
  `HMAC-SHA256(k_media_mac, header[0..31] || ciphertext)`.
* `k_media_enc` = `k_media[0..32)`، `k_media_mac` = `k_media[32..64)`.

### ۴.۱ payload ویدیو

واحد دسترسی H.264 خام از نوع **Annex-B** (ممکن است با `00 00 00 01 SPS …`
شروع شود). فریم‌های کلیدی (bit0 از flags) باید SPS/PPS را پیش از اولین اسلایس
داشته باشند تا رمزگشاز بتواند از هر فریم کلیدی شروع کند. پس از (راه‌اندازی
مجدد)، نباید بدون یک فریم کلیدیِ پیشین، تصاویر غیر-IDR تولید شوند.

### ۴.۲ payload صدا

`pcm_s16le`، تک‌کاناله، ۴۸۰۰۰ هرتز (همان‌طور که مذاکره شده). هر فریم صدا = ۱۰
میلی‌ثانیه = ۴۸۰ نمونه = ۹۶۰ بایت ⇒ دقیقاً یک بسته (`fragment count = 1`).
فریم‌های بزرگ‌تر به همان شیوه‌ی ویدیو قطعه‌بندی می‌شوند. سرور فریم‌های صدا را
دوباره در فریم‌های صدای OBS با حداکثر ۱۰۲۴ نمونه بسته‌بندی می‌کند.

## ۵. مهرهای زمانی و تأخیر

* کلاینت هنگام ارسال شروع `stream.active` لحظه‌ی `t0` (ساعت یکنواخت خودش) را
  ثبت می‌کند. هر بسته‌ی رسانه `timestamp = monotonic_now - t0` (نانوثانیه) را
  حمل می‌کند.
* سرور هنگام پردازش `config.stream.active = true` لحظه‌ی `r0` را ثبت می‌کند.
* تأخیر تخمینی برای بسته‌ی *i*:
  `lat_i = (recv_monotonic_i - r0) - timestamp_i` (نانوثانیه).
  مقدار گزارش‌شده میانگین متحرک نمایی (α = 0.1) است.
* مهرهای زمانی فریم‌های OBS با **ساعت یکنواختِ سرور** در خروجی رمزگشایی
  ثبت می‌شوند، بنابراین صدا و تصویر همگام می‌مانند هرچه ساعت دو رایانه با هم
  متفاوت است.

## ۶. payloadهای جفت‌سازی

### ۶.۱ کد QR (نمایش‌داده‌شده توسط افزونه‌ی OBS، اسکن‌شده توسط گوشی)

```
ocp1://pair?h=<ip>&p=<tcp-port>&s=<64-hex secret>&n=<server name>
```

* `h`, `p` — آدرس و پورت کنترلی که گوشی باید به آن وصل شود (سرور یک نشانی به
  ازای هر آدرس IPv4 قابل‌استفاده‌ی محلی فهرست می‌کند؛ QR نخستین آن را نشان
  می‌دهد).
* `s` — رمز تصادفی ۲۵۶ بیتی = `master`.
* `n` — نام نمایشی سرور (کدگذاری‌شده در URL).

گوشی پس از یک `auth_ok` موفق برای اتصال خودکار بعدی، `(server ip, server id?,
master)` را ذخیره می‌کند. این رمز هنگام تولید QR جدید **می‌سوزد** (تعویض
می‌شود).

### ۶.۲ کد جفت‌سازی (نمایش‌داده‌شده در پنجره‌ی ویژگی‌های OBS)

* شش رقم اعشاری، دست‌کم هر ۵ دقیقه دوباره تولید می‌شود و تا پیش از تولید دوباره
  معتبر است.
* با `kdf = "pbkdf2-sha256"` مطابق §3.2 استفاده می‌شود؛ سرور بر تلاش‌های
  ناموفق محدودیت نرخ اعمال می‌کند (دست‌کم ۱ ثانیه تأخیر پس از هر شکست، و کد
  پس از ۲۵ شکست در بازه‌ی ۵ دقیقه تعویض می‌شود).

### ۶.۳ وارد کردن دستی آدرس

اپلیکیشن گوشی امکان وارد کردن دستی آدرس IPv4 رایانه‌ی OBS و پورت کنترل را
فراهم می‌کند (افزونه‌ی OBS آن را به‌صورت «اتصال دستی: 192.168.1.42:47100» نشان
می‌دهد). جفت‌سازی (QR یا کد) همچنان الزامی است، مگر آن‌که کاربر در سمت OBS
صریحاً «نیازمند جفت‌سازی» را خاموش کند.

## ۷. الزامات امنیتی

1. همه‌ی قاب‌های کنترل پس از `auth_ok` و همه‌ی بسته‌های رسانه رمزگذاری و تأیید
   هویت‌شده‌اند (ChaCha20 + HMAC-SHA256/128، رمزگذاری-سپس-MAC).
2. `master` هرگز به‌صورت متنی از شبکه عبور نمی‌کند (فقط proofهای HMAC).
3. proofهای ناموفق: اتصال بسته می‌شود؛ سرور دست‌کم ۱ ثانیه پیش از پذیرش تلاش
   بعدی از همان آدرس تأخیر می‌اندازد؛ کد جفت‌سازی پس از شکست‌های مکرر تعویض
   می‌شود.
4. رمزهای ذخیره‌شده‌ی دستگاه در شاخه‌ی پیکربندی ماژول OBS با مجوزهای ویژه‌ی
   کاربر نگهداری می‌شوند؛ دکمه‌ی «فراموش کردن دستگاه‌های جفت‌شده» آن‌ها را
   حذف می‌کند.
5. گوشی هنگام پخش دوربین یا میکروفون یک نشانگر حریم خصوصی قابل‌مشاهده نشان
   می‌دهد و کنترل توقف فراهم می‌کند.
6. بسته‌های کشف رمز و رازی ندارند و هرگز به‌چیزی جز فهرست‌کردن در رابط
   کاربری اعتماد نمی‌شوند.
7. بسته‌های رسانه با برچسب‌های نشست ناشناخته انداخته می‌شوند.

## ۸. نسخه‌بندی

قواعد افزایش نسخه در `proto`/`v`: تغییرات ناسازگار در قاب‌بندی، رمزنگاری یا
دست‌دهی، نسخه‌ی پروتکل را افزایش داده و فیلدهای magic/`v` را تغییر می‌دهد.
کلیدهای JSON افزایشی (مثلاً فیلدهای اختیاری جدید در `config`) این کار را نمی‌کنند.
